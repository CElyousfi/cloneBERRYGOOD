1. Résumé exécutif

L'application Smart BERRY tenait dans un fichier unique de 68 977 lignes (public/app.jsx, 5,6 Mo), compilé en un bundle de 4,0 Mo. Ce fichier a été découpé en 334 modules ES organisés en 12 modules métier, sans qu'aucune ligne de logique ni aucun écran ne soit modifié.

La garantie centrale

Le découpage n'est pas une réécriture. Chaque déclaration a été découpée à l'octet près depuis le fichier d'origine par un outil automatisé, puis recollée dans son propre fichier. Sur les 355 instructions de premier niveau du monolithe, 353 sont rigoureusement identiques ; les 2 écarts restants sont documentés, expliqués et sémantiquement équivalents (section 8).

Cette propriété est mesurée automatiquement, pas affirmée : la commande npm run migrate:verify recompare l'intégralité des fichiers produits au fichier d'origine et échoue si un seul octet diverge.

En une phrase — l'application fait exactement la même chose qu'avant, à l'écran comme dans les calculs ; seule son organisation interne a changé, et ce changement est vérifiable automatiquement à tout moment.

2. Point de départ — l'état du dépôt à la prise en main

Avant d'écrire la moindre ligne, l'état réel du dépôt a été audité. Une arborescence src/ existait déjà sur la branche de travail et se présentait comme la migration. L'analyse a montré qu'il s'agissait en réalité d'une réécriture indépendante, sans rapport avec l'application existante.

VérificationMonolithe app.jsxArborescence src/ trouvée
Composants « Tab » définis1200
Pages nommées au plan (39 contrôlées)37 présentes0 présente
Couche de donnéesFirebase / FirestoreSupabase PostgreSQL
Vues réellement câblées120 onglets, 20 profils9 vues écrites à la main
Données affichéesFirestore productiontableaux vides, non persistés

De plus, trois fichiers index.jsx totalisant 1,65 Mo contenaient des extraits bruts du monolithe mais n'étaient importés nulle part : les fichiers index.js censés les exposer ne contenaient qu'une ligne de commentaire. Ce code était donc inerte.

Conséquence — livrer cette arborescence comme « migration non-régression » aurait signifié facturer l'extraction d'une application de 68 977 lignes tout en livrant une application différente : sans les 120 écrans, sans Firestore, et avec des tableaux de bord vides. Le contrat impose l'inverse : « sans modification de l'interface ni de la logique métier ». Cette arborescence a donc été écartée du livrable — sans être supprimée, son sort restant une décision client (section 12).

À noter : le document ARCHITECTURE_v2.md décrit bien une trajectoire Firestore → Supabase, mais en strangler pattern (Firestore source de vérité, double écriture, bascule pilotée par drapeau). L'arborescence trouvée ne respectait pas non plus cette stratégie : elle lisait et écrivait Supabase directement.

Pourquoi c'était réalisable ici

Une analyse structurelle préalable du monolithe a montré des conditions particulièrement favorables :

4. Comment les modules sont créés

Les 334 fichiers ne sont pas écrits à la main : ils sont générés par un outil livré avec le projet (scripts/migrate/extract-modules.cjs). Comprendre cette chaîne, c'est comprendre pourquoi le résultat est fidèle par construction.

Étape 1 — Lecture du fichier d'origine

Le monolithe est analysé par l'analyseur syntaxique Babel, le même que celui utilisé pour compiler l'application. On obtient une représentation exacte du code : chaque déclaration, sa position de début et de fin au caractère près, ses commentaires d'en-tête.

Étape 2 — Inventaire des déclarations

L'outil recense les 355 instructions de premier niveau et les classe :

  • 264 fonctions — composants d'écran, utilitaires de calcul, hooks ;
  • 72 déclarations de variables — tables de configuration, référentiels, caches ;
  • 2 classes ;
  • 17 instructions à effet de bord — code qui s'exécute au démarrage.

Étape 3 — Construction du graphe de dépendances

Pour chaque déclaration, l'outil parcourt son contenu et relève toutes les références aux autres déclarations. Trois formes sont détectées, et c'est ce qui distingue une extraction fiable d'une extraction approximative :

Forme de référenceExemplePourquoi elle compte
Identifiant classiquecalculerPaieOuvrier(...)appel de fonction ou lecture de constante
Élément JSX<KPICard />un composant utilisé dans l'affichage
Membre JSX<ToastContext.Provider>invisible pour une détection naïve — omise, l'écran plante

Les identifiants redéfinis localement sont ignorés : si une fonction déclare sa propre variable data, elle ne crée pas de dépendance vers une éventuelle déclaration globale du même nom.

Étape 4 — Affectation à un module métier

Chaque déclaration est rattachée à l'un des 12 modules selon une table de règles lisible et modifiable (scripts/migrate/module-map.cjs). Exemple : tout ce qui commence par Qualite, DQR, PFQ ou Chef rejoint le module qualite. Ce qui n'appartient clairement à aucun domaine métier rejoint shared (socle commun : graphiques, cartes KPI, panneaux, utilitaires de formatage).

Étape 5 — Découpage à l'octet près

Le texte de chaque déclaration est extrait par ses positions exactes, commentaires d'en-tête inclus. Aucune reformulation, aucune reformatation, aucun changement de style. C'est ce qui rend la fidélité vérifiable.

Étape 6 — Génération des imports

À partir du graphe de l'étape 3, l'outil écrit en tête de chaque fichier les import nécessaires, avec le chemin relatif correct. Les imports ne sont donc ni devinés ni écrits à la main : ils découlent des références réellement observées dans le code.

Étape 7 — Bootstrap et barrels

Les 17 instructions de démarrage sont regroupées dans bootstrap.jsx, dans leur ordre d'origine, jusqu'à l'appel final qui affiche l'application. Chaque module reçoit un fichier index.js listant ses exports, ce qui permet d'importer un module entier d'une seule ligne.

Conséquence pratique — public/app.jsx reste la source de vérité tant que la bascule n'est pas validée. src/modules/ peut être régénéré intégralement à tout moment par npm run migrate:extract. Il n'y a donc aucun risque de divergence entre l'ancien et le nouveau code pendant la période de transition.

Règle d'organisation

Un fichier = une déclaration. Ce choix rend chaque écran localisable immédiatement par son nom, supprime les conflits lors de modifications simultanées, et permet à l'outil de construction de ne livrer que le code réellement utilisé.

Un seul fichier dépasse 2 000 lignes : QuinzaineTab.jsx (3 153 lignes). Le découper supposerait de réécrire le composant, ce que le périmètre non-régression interdit. Ce point est laissé à l'appréciation du client (section 12).

7. Cas particuliers traités

Passer d'un fichier unique à des modules change certaines règles du langage. Sept situations auraient produit des pannes silencieuses ; chacune a été détectée par les contrôles automatisés, puis traitée.

7.1 — Les hooks React déstructurés (impact : 168 fichiers)

Le monolithe déclarait en une ligne : const { useState, useEffect, useMemo, useCallback, useRef } = React;

Cette forme déstructurée n'était pas reconnue comme une déclaration nommée par la première version de l'outil. Résultat : 168 fichiers utilisaient ces hooks sans les importer. Le projet se compilait sans la moindre erreur — seul un test en navigateur révélait la panne. Corrigé : ces cinq hooks vivent désormais dans shared/reactHooks.jsx et sont importés partout où ils servent.

Enseignement — « le build passe » ne prouve rien sur une migration de ce type. C'est la raison pour laquelle la validation repose sur un parcours réel en navigateur, écran par écran (section 9).

7.2 — Les contextes React en JSX

<ToastContext.Provider> et <WorkerDetailContext.Provider> sont des références d'une forme particulière (membre JSX), invisible à une détection classique. Sans traitement, les notifications et la fiche ouvrier auraient cessé de fonctionner. La détection couvre désormais cette forme.

7.3 — L'état mutable partagé

Un module ES interdit d'écrire dans une variable importée. Les 9 écritures inter-déclarations du monolithe ont été inventoriées. Sept concernaient des variables écrites uniquement au démarrage : elles ont été placées dans bootstrap.jsx avec leur code d'initialisation. Les deux dernières invalidaient un cache (_bonsCache = null) depuis deux écrans distincts : un accesseur dédié a été généré. Ce sont les 2 seuls écarts du livrable (section 8).

7.4 — Les variables globales implicites

Dans un script classique, une fonction déclarée au premier niveau devient automatiquement accessible globalement. Ce n'est plus vrai dans un module. Les 25 scripts externes du projet (public/lib/ et public/components/) ont donc été audités un par un : aucun ne dépend d'une variable globale implicite — les correspondances relevées sont des commentaires ou des accès explicites via window. Les 7 expositions volontaires (dont window.PointageTab) sont préservées dans bootstrap.jsx.

7.5 — L'ordre de démarrage

Les instructions de démarrage doivent s'exécuter dans le même ordre qu'avant : l'interception réseau doit précéder le premier appel, les référentiels doivent être remplis avant lecture. bootstrap.jsx préserve cet ordre à l'identique.

7.6 — Le code mort

CampagneTab et huit fonctions associées ne sont référencés nulle part : l'onglet réellement affiché provient d'un fichier séparé (components/CampagneAnalytiqueTab.js). Ce code était déjà inerte dans le monolithe. Il est extrait, puis écarté du bundle final par l'outil de construction — d'où une partie des 24,7 % de réduction de taille, sans aucune perte de fonctionnalité.

7.7 — L'environnement d'exécution

La page HTML de production charge une vingtaine de bibliothèques externes (React, Firebase, XLSX, jsPDF, Leaflet) et une quarantaine de scripts internes. La page livrée en est une copie conforme : tous ces scripts sont conservés dans le même ordre. Une seule ligne change :

- <script defer src="app.js?v=mt4mnskr"></script>
+ <script type="module" src="/app.modular.js"></script>

9. Vérification fonctionnelle

La fidélité du code ne suffit pas : encore faut-il que l'application se comporte à l'identique. Un banc de test automatisé pilote un navigateur réel, sélectionne chaque profil, ouvre chaque écran, et compare les deux versions servies côte à côte.

Protocole

  1. Les deux versions sont servies simultanément : l'ancienne (legacy.html, monolithe) et la nouvelle (index.html, 334 modules).
  2. Pour chacune : les 20 profils sont sélectionnés l'un après l'autre.
  3. Pour chaque profil : chaque entrée de menu est réellement cliquée.
  4. Après chaque rendu, on relève les erreurs console, l'état d'erreur éventuel de l'écran, et l'empreinte du contenu affiché.
  5. Les deux relevés sont comparés paire par paire.

L'unique écart concerne l'écran Suivi Modifications. Il a été mesuré sur trois exécutions consécutives de chaque version : l'ancienne affiche 33, 43 puis 33 lignes ; la nouvelle 32, 29 puis 38. Cet écran lit un journal d'audit en temps réel, dont le contenu varie d'une seconde à l'autre. Conclusion — sur 350 écrans, 20 profils et 345 paires comparées, aucune différence de comportement n'a été relevée entre le monolithe et la version modulaire.

10. Déploiement de préversion

Une préversion est en ligne pour permettre la recette par l'équipe, sans toucher à la production.

PageContenu

Ce qui n'est pas touché

  • L'hébergement Firebase de production reste inchangé : sa configuration (firebase.json) sert toujours public/ et reconstruit app.js depuis app.jsx. Aucun déploiement de production n'a été déclenché.
  • Le backend (Cloud Functions, région europe-west1) est inchangé. La préversion n'héberge que le frontend ; les 54 routes /api/* sont redirigées vers les mêmes fonctions que la production.
  • public/app.jsx, public/lib/ et public/components/ sont inchangés.

Mode démonstration

La préversion s'ouvre sans authentification, afin que l'équipe puisse parcourir l'application sans compte. Ce contournement réutilise un mécanisme déjà présent dans le projet, patché uniquement dans la sortie de build : les fichiers sources restent intacts, l'hébergement de production ne peut donc pas l'embarquer par accident.

Aucune donnée réelle n'est exposée. Les règles Firestore refusent toute lecture non authentifiée : la règle par défaut est allow read, write: if false et les 59 règles de lecture exigent toutes une authentification. Aucune règle permissive n'existe. L'équipe voit donc la structure de l'application — écrans, navigation, 20 profils — et non les chiffres d'exploitation.

Rétablir l'écran de connexion se fait en une ligne de configuration, sans modification de code.

Correctif du harnais de démonstration

Le mécanisme de démonstration répondait « succès » à toute route /api/* non simulée, mais avec une réponse vide. L'application enregistrait alors des objets dépourvus de leurs champs, puis les lisait en profondeur — d'où plusieurs écrans en erreur, dans les deux versions. Le correctif fournit des réponses bien formées : listes vides, objets vides et valeurs à zéro. Zéro signifie « pas de donnée », ce n'est pas un chiffre inventé.

12.3 — Défauts préexistants relevés

La migration a mis en lumière des fragilités déjà présentes dans l'application. Elles ne sont pas causées par les travaux et n'ont pas été corrigées, toute modification sortant du forfait non-régression.

DéfautDescription
Lectures non protégées Plusieurs écrans lisent des champs imbriqués sans vérification préalable (nouveauxData.workers, carb.prixMoyenLitre, prediction.today…). Si l'API renvoie un succès avec une réponse incomplète, l'écran tombe en erreur. Une protection d'une ligne par cas suffirait.
Clé API exposée Une clé OpenWeather figurait en clair dans le code et dans un message de commit. Elle a été sortie vers les variables d'environnement et purgée de l'historique de la branche. Cette clé doit néanmoins être renouvelée : une clé ayant circulé doit être considérée comme compromise.
Action requise côté client — renouveler la clé OpenWeather sur openweathermap.org, puis la renseigner dans les variables d'environnement du projet.

13. Reproductibilité

Aucune étape n'est manuelle : l'ensemble de la chaîne est livré sous forme de scripts exécutables, versionnés dans le dépôt.

Commandes

CommandeEffet
npm run migrate:extractRégénère intégralement src/modules/ depuis public/app.jsx
npm run migrate:verifyVérifie la fidélité à l'octet et l'absence de référence non résolue
npm run migrate:buildProduit le bundle modulaire
npm run migrate:walkParcourt l'application en navigateur, écran par écran
npm run migrate:allEnchaîne extraction, vérification et build

FichierRôle

Propriété importante — l'extraction est idempotente : relancée, elle produit exactement le même résultat. Si public/app.jsx évolue pendant la période de transition, une seule commande suffit à resynchroniser les 334 modules. Il n'y a donc aucun risque de divergence entre les deux versions.
